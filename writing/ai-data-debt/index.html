Excel → AI 数据清洗仍需避免制造新形式的“数据债务”

本文源于一段本人的数据加工实践，讨论 AI 辅助数据清洗中的正确性、可维护性与交接问题。文中的工程模板是个人提出的实践建议，其效果仍需结合具体任务验证。

1. 观察

1.1 数据加工现状

公司处于快速增长阶段时，业务扩张速度往往快于管理工具、流程和规范的更新速度。数据、文档和处理规则随业务不断增加，却未能及时完成统一整理。借用热力学中“熵增”的概念，这也可以被理解为组织成长过程中的一种“熵增”：短期内，它可能是为了支持高速发展而被容忍的副作用，但如果企业希望面向未来建设更稳定的数据基础，就需要逐步降低信息混乱和规则不一致。

当数据从源系统导出后，还需要经过多次人工加工或跨团队传递，才能形成最终分析结果时，流程的复杂度便不只取决于数据量，也取决于加工环节和协作方式。这类流程在任务规模较小时可能满足需求，但随着数据量和协作范围扩大，以下问题可能逐渐显现。

  1. 数据量增加会直接放大人工处理的工作量；
  2. 手工加工excel难以完全避免失误，错误不仅会造成返工，也可能影响后续分析与决策；
  3. 信息传递效率低
    1. 跨团队协作时，为了对齐指标口径和保持规则一致，还需要付出较高的沟通成本。如果前序生产者不了解使用者的实际需求，产出的数据可能无法直接使用，使用者只得再次加工，形成重复劳动。
    2. 许多处理逻辑和业务背景只存在于个人经验中。新成员接手工作时，需要反复向原负责人确认字段含义、异常情况和处理方式，知识传递高度依赖个人。这不仅延长了学习过程，也持续占用原负责人的时间。

1.2 AI降低了数据加工门槛，但没有解决正确性与治理问题

AI Coding 降低了代码生成和工具开发的门槛。过去依赖手工 Excel 完成的重复工作，现在可以被转化为脚本、看板或web工具，业务背景和处理规则也可以沉淀为md文档。

但是需要区分代码能够运行、处理过程能够复现，以及业务结果正确，并不是同一件事。需要注意的是：

  1. AI Coding融入数据加工过程 ≠ 数据治理。将处理逻辑写成代码，只能提高执行的一致性和可复现性，不能证明业务规则正确，判断仍然需要人类。
  2. 开发门槛降低 ≠ 治理成本降低。如果企业只鼓励快速制作工具，却没有同步建立项目规范，过去散落在共享盘中的混乱 Excel，可能会变成更多缺乏维护的脚本、html 文件、BI 看板和小型数据库。它们看起来更“数字化”，但如果没有明确这列数据清洗项目的规范（e.g. 数据来源、业务口径、维护责任），这些工具在短期内解决了个人问题，却未必能够被他人理解、接手和长期使用，甚至可能形成新的数据债务。

Web 开发模板可以降低工具搭建和架构选型的门槛，几乎已经能满足非科班出身人员进行开发架构选型。但是对于数据清洗项目而言，目前并没有相应的工程架构规范，不少自行探索使用ai提效数据清洗人员在没有经过培训之前，更多的是想象自己通过模糊描述就能让AI产出满足需求的结果。对于缺乏开发经验的业务人员而言，仅仅获得AI工具，并不意味着能够自然完成任务拆解、模块设计、规则沉淀和结果验证。

在数据标准和公共数据能力尚未完善的场景中，AI 介入数据清洗我认为更像是标准数据基础逐步成熟前的一种过渡能力。但是AI介入数据清洗后，需要解决的不只是“如何更快地生成解决问题的代码”，还包括两个更基础的问题：

  1. 哪些数据任务适合通过AI进行自动化，应该采用多重的治理方式；
  2. 一个需要重复运行或长期使用的数据清洗项目，应该如何描述、验证、变更和交接。

这两个问题分别对应后文的数据项目分级和项目工程规范。但即使项目分级和工程规范已经明确，个人提效也不会自动转化为组织能力，毕竟需要合适的制度设计和人自主执行。员工是否愿意投入时间学习和沉淀规则，公司如何评价AI产出，以及有限资源应该如何配置，仍然是AI落地过程中需要解决的组织问题。

1.3 从个人提效转化为组织能力仍面临困难

目前，AI在数据加工中的应用还面临几个问题：

  1. 职能部门的AI应用价值短期难衡量。对于职能部门而言，AI带来的价值通常不直接表现为收入增长，而更多体现为节省工时、降低错误、缩短流程和减少经营风险。这类收益较为间接，难以在短期内被准确衡量。随着公司对AI投入从广泛探索转向关注实际产出，Token、培训和技术支持等资源也会受到更严格的评价。
  2. 当前部分AI应用主要停留在个人提效层面，未成为可供组织长期使用的数字资产。员工借助AI完成了数据清洗脚本或小型工具，但如果缺少数据来源、业务口径、质量验证和维护责任记录，这些成果就难以被他人接手和长期复用。个人节省了时间，并不意味着组织同步获得了知识沉淀和流程优化。
  3. 员工需要投入时间学习且学习热情需要被支持。从未使用AI到能够独立改造工作流，本身存在一定的学习和验证成本。员工需要投入时间拆解任务、表达业务规则、核对结果并处理异常。如果这部分投入完全由个人承担，而提效成果在评价和资源分配中不可见，仅依赖员工兴趣很难形成持续、广泛的参与。
  4. AI适用场景需要达成共识。AI也并非适用于所有数据加工任务。当任务重复发生、规则相对稳定、输入输出明确、处理环节可以拆分、结果能够验证且风险可控时，更适合通过人机协作实现自动化；如果任务高度依赖专业判断、规则频繁变化、数据较为敏感或错误影响较大，则仍需数据和IT团队介入。

所以公司需要解决的不只是“是否鼓励员工使用AI”，而是如何将个人探索逐步转化为可治理的组织能力。这可能包括三个层面：

  1. 在项目层面，对不同数据任务进行分级，并建立与其价值和风险相匹配的工程规范；（见2.1-2.2）
  2. 在业务协作层面，让业务人员通过真实数据、处理规则和结果样本，更完整地表达需求；（见2.3）
  3. 在组织管理层面，为初次尝试提供必要的进入条件，并对产生真实价值和知识沉淀的项目给予资源与激励。（见2.4）

2. 思考

2.1 数据项目等级划分

首先，并不是所有 Excel 工作都值得被开发成长期系统。一次性数据分析、部门内重复任务和跨团队长期使用的数据产品，对数据的规范、存储和运维的要求不同。

在选择技术方案之前，需要判断项目特征：

  1. 项目需求：项目解决什么问题、使用频率、使用范围、是否可能跨团队复用
  2. 生命周期：项目是临时、试点还是长期使用，以及何时复核、迁移或下线
  3. 责任：谁定义口径、谁负责验收和维护
  4. 数据特征：数据来源稳定性（原始数据/加工后的数据）、数据血缘、数据量规模和增长趋势、是否需要保留历史数据版本。
  5. 技术运行方面：任务是离线批处理还是实时查询，数据的访问控制是单人使用还是多人并发

对此可以有三类不同的处理方案：

1.一次性任务采用轻量代码，需求方自行定义开发；

2.需要重复运行的工作采用标准项目模板；-->“2.2 具体的数据清洗项目工程规范”

3.长期、多人使用或影响关键决策的项目，需数据和 IT 团队进介入，帮助建立数据规范、存储和后续运维。

2.2 具体的数据清洗项目工程规范

不同业务的数据清洗逻辑不可能完全一致。项目如何描述、执行、验证、变更和交接更值得统一。

目前已有的 BI 或 Web 开发框架，能够帮助没有开发经验的员工快速制作和部署工具；但对于更常见的数据清洗任务，新手未必具备拆分加工环节、沉淀业务规则和设置质量检查的意识。项目即使短期运行成功，其正确性、可维护性和可交接性仍可能存在问题。

2.3 组织协作模式的可能变化

AI不仅改变了开发方式，同时也改变了业务需求的表达方式

传统的信息化建设通常从业务提出需求开始，再由数据和IT团队理解业务背景、确认数据口径并完成技术实现。但在实际沟通中，业务人员脑中的字段含义、处理规则和异常判断很难通过一次需求描述完整传递。双方往往需要经过多轮沟通和结果验证，才能逐步还原真正的业务需求。

AI Coding为这一过程提供了另一种可能的范式。对于业务人员每月重复使用的数据，业务可以先借助AI完成初步的数据清洗和加工原型。在这个阶段，代码不一定符合长期运行的工程标准，但项目中沉淀的数据源、字段定义、异常案例、预期输出和验收样本，对后续的数据与IT建设具有重要价值。

所以老生常谈的 数据治理其实并不等于 IT 治理，在AI 加持下也并不等于业务完全IT化。业务自助开发不应被理解为将全部技术责任转移给业务，也不意味着数据和IT团队只需接收业务写出的代码。更像是把传统的“业务提需求”范围扩大：业务不再只提供一段文字描述，而是通过真实数据和处理原型，将自己的需求表达得更加结构化、具体化和可验证。

在这个过程中，三方的职责也会发生变化：

  1. 业务人员负责解释业务背景，通过原型明确数据来源、字段含义、处理逻辑、异常情况和预期结果；
  2. 数据团队负责识别其中可以标准化和跨项目复用的定义、规则与数据模型，并判断哪些内容应进入公共数据层；
  3. IT团队负责评估权限、安全、基础设施、系统集成和长期运行要求，并对需要部署的项目进行工程改造。

业务自主开发的原型最终不一定都要变成正式系统。对于使用范围较小、风险较低的项目，可以继续由业务按照轻量规范维护；对于重复运行、多人使用或影响重要决策的项目，则需要由数据和IT团队评估其是否应被规范化改造，或者沉淀为公共数据能力；对于已经失去价值的项目，则应及时下线。

从这个角度看，业务侧的AI数据清洗项目既是提效工具，也可以成为未来信息化建设的需求入口。它的主要价值未必是直接复用业务人员生成的代码，而是减少业务知识在跨团队传递中的损耗，为后续的数据标准、数据模型和系统功能提供更加真实的输入。

2.4 在资源收紧下，需要为AI提效建立支持和激励机制

业务人员使用AI提效，主要动力仍然来自减少个人重复劳动以及对新工具的兴趣。公司层面若尚未形成明确的激励机制，会产生一个现实问题：员工需要自行承担学习、试错、规则整理和结果验证的成本，但项目带来的效率改善、知识沉淀和长期复用价值更多由组织获得。如果这部分投入在评价和资源分配中不可见，仅依靠个人热情很难形成长期持续和扩大。

与此同时，公司对AI资源投入已经从广泛探索转向关注实际产出，不适合继续依赖无差别的额度支持或大范围通用培训。因此，组织既需要为尚未使用AI的员工保留低成本的进入通道，也需要把更深入的资源和激励集中到真实、有价值且能够验证的工作流上。

2.4.1 关于AI的使用可以考虑以下两类项目基础支持

  1. 提供工具+case指引：为员工提供低成本的基础条件，除了ai工具、token额度外还需要标准项目模板和公司内部的成功数据清洗案例。目的是让员工通过类比识别可以用AI提效的机会和具备完成第一次尝试的条件。
  2. 培训应当从通用工具介绍转向岗位工作流。代码小白进行数据清洗的真正困难通常是不知道自己的哪些工作的哪些部分适合AI化，也不知道如何拆分输入、输出、业务规则。因此，可以围绕月度数据合并、字段映射、数据核对和固定报表等真实任务，提供案例、答疑和辅导。

当员工识别出明确场景后，可以通过项目制获得进一步支持。项目只需说明当前人工流程、预期改善、数据风险和验收方式，公司再据此提供有限的增量额度、技术评审、试点时间或部署资源，并根据结果决定继续投入、调整还是停止。

2.4.2 项目评价和激励

项目评价不应只看Token使用量、工具数量或是否上线，还应考察是否减少工时和错误、缩短交付周期、支持他人接手，以及是否沉淀了可复用的数据规则。对于第一次尝试者，可以侧重其是否完成了工作流拆解和有效验证。对于成熟项目，则进一步评价稳定运行、复用范围和维护成本。

但评价指标本身还不足以形成激励。组织还需要承认员工在探索、文档整理和质量验证上的投入，例如为试点预留一定的时间和token花费，将经过验证的流程改善、知识沉淀和跨团队复用纳入评价/认可，并让节省出来的时间真正转向更高价值的工作。如果提效只意味着员工获得更多任务，或者规范建设在绩效中完全不可见，员工就缺乏主动公开和推广提效成果的动力。

因此，激励的目标不应是要求所有人使用AI，也不应追求表面的AI使用率，而是降低第一次有效尝试的成本，并让创造真实业务改善、完成规范沉淀和推动成果复用的人获得可感知的资源与认可。

小结

AI降低了业务人员使用代码处理数据的门槛，但工具能够运行并不意味着结果正确，也不意味着个人提效已经转化为组织能力。缺少项目分级、工程规范、业务规则沉淀和维护责任，AI甚至可能将原有的Excel混乱转化为新的数据债务。

因此，AI数据清洗的落地不能只依靠员工个人探索，还需要从项目、协作和组织三个层面共同推进：

  • 根据价值和风险对项目分级，建立可复用、可验证的工程规范；
  • 让业务、数据和IT团队形成更高效的协作方式；
  • 同时通过基础支持、项目评价和激励机制，让真正产生业务改善和知识沉淀的实践能够持续发展。
